A 5×5, 64-filter int8 convolution engine with hardwired weights

The top module is tt_um_ejborcherding_conv7x7 on branch ring-datapath (commit 65fe63e). The host streams a grayscale image in, 5 pixels per column. For each output pixel the chip returns 64 exact signed 20-bit sums. The 1,600 weights are synthesized into logic gates, so they are fixed at tapeout.

Architecture

Two rotating rings feed one multiplier

The 25 window pixels and the current filter's 25 weights each sit in a ring of byte registers. Both rings rotate one slot every clock, so the multiplier always reads slot 0 of each. Every register is fed only from its neighbour. No wide multiplexer picks one value out of many.

Why the rewrite

The old design failed on wiring, not on area

Floorplan

All pins sit on one short stretch of the top edge

The Tiny Tapeout template puts every I/O pin between x = 30 and 147 µm. The input path, pixel ring, multiplier and output mux pull toward those pins. The flow's hold-fix delay buffers land in the same corner. That corner decides whether the design routes.

Place-and-route experiments

Routes only when the hold fix stops crowding the pin corner

Global-route congestion is the share of available routing tracks the router plans to use. Every run that routed planned 70 % or less. The default hold margin added hundreds of delay buffers in the crowded corner and pushed congestion back up past 85 %.

The hold slack is small but real. The TT constraints already subtract a 0.25 ns clock uncertainty from every hold check, and run G meets hold with that applied. What run G drops is the flow's extra 0.1 ns placement margin, the setting that caused the ~650-buffer pile-up. Run I shows how thin this is: banning the slow clock-buffer cells shifted hold to −0.008 ns.
